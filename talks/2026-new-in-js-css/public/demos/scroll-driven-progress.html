Chapter 1: The Scroll Event Era

For years, web developers have relied on JavaScript scroll event listeners to create scroll-linked effects. Every progress bar, every parallax background, every fade-in-on-scroll animation required imperative code running on the main thread.

The scroll event fires at high frequency — potentially 60+ times per second. Each handler that reads layout properties like scrollTop or getBoundingClientRect() forces the browser to recalculate layout, causing performance bottlenecks.

Chapter 2: The IntersectionObserver Improvement

IntersectionObserver was a major step forward for detecting when elements enter or leave the viewport. It moved the intersection calculation off the main thread and provided an efficient, callback-based API.

But IntersectionObserver is binary — an element is either intersecting or it's not. You can use thresholds to get multiple callbacks, but you can't smoothly tie an animation to the intersection ratio without falling back to polling or scroll listeners.

Chapter 3: The Library Landscape

Libraries like GSAP ScrollTrigger, AOS (Animate on Scroll), Locomotive Scroll, and Lenis emerged to solve the performance and developer experience problems. These libraries provide excellent APIs and handle debouncing, RAF scheduling, and cross-browser quirks.

But they add bundle size, have learning curves, and fundamentally still run on the main thread. The core limitation isn't the library — it's that JavaScript scroll handlers can never run on the compositor thread.

Chapter 4: The CSS Solution

Scroll-driven animations move this entire concern into the browser's rendering pipeline. By replacing animation-duration with animation-timeline: scroll(), the browser ties animation progress directly to scroll position.

This runs on the compositor thread — the same thread that handles CSS transforms and opacity changes. It's inherently smooth because it doesn't compete with JavaScript execution for CPU time.

Chapter 5: The Future

As browser support expands to Firefox and more properties become animatable via scroll timelines, we'll see this pattern replace a large portion of scroll-related JavaScript on the web.

The progress bar you're watching right now is a @keyframes animation with animation-timeline: scroll(). No JavaScript is listening to scroll events. No requestAnimationFrame loop. Pure CSS.
